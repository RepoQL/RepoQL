# Ruby Format Support: What Great Looks Like

> An agent should be able to understand a Ruby codebase's structure — classes, modules, mixins, methods, and their relationships — without reading source files, and query it all through the same SQL surface as every other format.

An agent lands in a Rails application with 800 Ruby files. It doesn't open any. It scans headlines and sees: a User model with 12 public methods and 3 associations, a concern providing soft-delete behavior mixed into 9 models, a controller with 7 actions filtered by 2 before_actions. It asks "what includes Authenticatable?" and gets every class across the codebase that mixes it in. It asks "show me all methods on User" and sees not just what's defined in `user.rb`, but methods added by concerns, inherited from ApplicationRecord, and generated by `attr_accessor`. It traces the method resolution order and knows exactly which module's `validate` will be called. The class was defined across three files — the agent sees one complete picture. Ruby's dynamism didn't hide structure. The graph captured it.

---

## The Mixin Graph

- An agent should be able to see every module mixed into a class, and how — include, extend, or prepend
- An agent should be able to trace the method resolution order for any class
- An agent should be able to ask "what does this module provide?" and see the methods it contributes
- An agent should be able to find every class that includes a given module
- An agent should be able to distinguish the three mixin mechanisms by their effect: include adds instance methods, extend adds class methods, prepend wraps existing methods

```sql
-- "What concerns does User include?"
SELECT * FROM ruby_mixins WHERE target_class = 'User'

-- "What classes include Authenticatable?"
SELECT * FROM ruby_mixins WHERE module_name = 'Authenticatable'
```

## Distributed Definitions

- An agent should be able to see the complete definition of a class even when it's spread across multiple files
- An agent should be able to find every file that reopens a given class
- An agent should be able to distinguish between a class's original definition and its reopenings
- An agent should be able to see all modifications to standard library classes in one query

Ruby classes are open. `User` might be defined in `app/models/user.rb`, extended in `app/models/concerns/user_search.rb`, and monkey-patched in `config/initializers/user_extensions.rb`. An agent should see all three as contributing to the same entity.

---

## Visibility and Access

- An agent should be able to query methods by visibility: public, protected, or private
- An agent should be able to see which methods are class methods and which are instance methods
- An agent should be able to find singleton methods defined on specific objects
- An agent should be able to see where visibility changes within a class definition

---

## Methods and Callables

- An agent should be able to see all methods on a class, including those generated by `attr_accessor`, `attr_reader`, and `attr_writer`
- An agent should be able to distinguish between explicitly defined methods and generated ones
- An agent should be able to see method parameters, including defaults, splats, keyword arguments, and block parameters
- An agent should be able to find methods that accept blocks (methods that yield)
- An agent should be able to see aliased methods and trace them to their originals

```
headline  →  "user.rb | User < ApplicationRecord | authenticate, generate_token, admin? | 180 ln, ~850 tok"
structure →  +authenticate(password)                          #symbol=authenticate
             +generate_token → String                         #symbol=generate_token
             -validate_password_strength                      #symbol=validate_password_strength
             ~name (attr_accessor)                            #symbol=name
```

---

## Inheritance

- An agent should be able to trace the full inheritance chain of any class
- An agent should be able to find all subclasses of a given class, at any depth
- An agent should be able to see which methods are inherited versus defined locally
- An agent should be able to query the class hierarchy as a tree

---

## Dependencies

- An agent should be able to see what each file requires, through both `require` and `require_relative`
- An agent should be able to trace the dependency graph between files within a project
- An agent should be able to distinguish between internal requires and external gem requires
- An agent should be able to find files with circular or missing requires

---

## Constants and Namespacing

- An agent should be able to find all constants defined within a module or class
- An agent should be able to resolve qualified constant references (`Module::Class::CONSTANT`)
- An agent should be able to query the namespace hierarchy as a tree

---

## Metaprogramming (Best Effort)

- An agent should be able to see methods created by common metaprogramming patterns: `attr_accessor`, `delegate`, `define_method`, `scope`
- An agent should be able to distinguish statically-visible structure from dynamically-generated structure
- An agent should be able to trust that what's reported as generated is marked with appropriate confidence
- An agent should not expect the graph to capture arbitrary `eval` or `method_missing` — the boundary is patterns with recognizable syntax

Metaprogramming is Ruby's defining power and its indexing challenge. The north star is not "capture everything" — it's "capture what has a syntactic footprint, and be honest about what's invisible."

---

## Framework Conventions

- An agent should be able to find all models, controllers, and other framework-conventional types by their role
- An agent should be able to see declared associations (`has_many`, `belongs_to`, `has_one`) as relationships in the graph
- An agent should be able to see validations, callbacks, and scopes declared on a model
- An agent should be able to query these framework patterns through SQL without knowing the framework's implementation details

Framework-specific structure (Rails associations, RSpec describe blocks, Rake tasks) is valuable because it's what agents actually ask about. A Ruby indexer that ignores Rails conventions misses the questions agents most want to answer.

---

## What Great Looks Like

| Declaration | Why It Matters |
|-------------|----------------|
| See the complete class across all files | Ruby's open classes distribute definitions — agents need the whole picture |
| Traverse the mixin graph | Mixins are Ruby's composition mechanism — they answer "what can this object do?" |
| Query by visibility | Knowing public API versus internals changes how you approach the code |
| See generated methods alongside defined ones | `attr_accessor` creates real methods — hiding them hides the API |
| Find framework patterns through SQL | "All models with soft-delete" is the question agents ask, not "all classes inheriting from ApplicationRecord that include a module named SoftDeletable" |
| Know when structure is inferred | Honest confidence beats false completeness |

---

## Anti-Patterns

| Don't | Declaration Form |
|-------|------------------|
| Show only what's in one file | An agent should see a class's complete definition across all contributing files |
| Ignore generated methods | An agent should see methods from `attr_accessor` and `delegate` as real methods |
| Flatten the mixin graph into a list | An agent should trace the method resolution order |
| Treat metaprogramming as noise | An agent should see recognizable metaprogramming patterns as structure |
| Require framework knowledge to query | An agent should find models and controllers through SQL, not naming conventions |
| Claim completeness when dynamism prevents it | An agent should know what the graph captured versus what it couldn't |

---

*An agent should be able to understand Ruby code the way a Ruby developer does — through classes, modules, mixins, and conventions — not the way a parser does.*
